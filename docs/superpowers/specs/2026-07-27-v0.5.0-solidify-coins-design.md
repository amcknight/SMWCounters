# v0.5.0 — Solidify + Coins

Design approved 2026-07-27. Theme: the core idea is mature; this release
solidifies it (status-pixel polish, a live-confirmed gating bug fix) and adds
one new counter on proven architecture (Coins with checkpoint banking).

## 1. Status pixel: vertical centering + severity-ladder colors

**Position.** The dot stays pinned left at `x = 3f` but is vertically centered:
`y = (height - dotSize) / 2f` (dotSize stays `5f`). Drawn in
`SmwCountersComponent.DrawGeneral`, outside the row flow, as today.

**Colors.** `StatusDot` remaps to a severity ladder — cool colors are good,
warm colors are trouble, blue is the best state:

| Color    | Hex        | State |
|----------|------------|-------|
| Red      | `#E53E3E`  | Detached |
| Orange   | `#FF851B`  | Degraded (rivals live) — *was yellow* |
| Yellow   | `#FFDC00`  | Searching or Discovering — *was gray / blue* |
| Green    | `#2ECC40`  | Resolved/Held, witness-unvouched — *was pale green* |
| Blue     | `#398FE5`  | Resolved/Held, witness-vouched — *was green* |
| Gray     | `#9A9A9A`  | Retry cooldown (deliberately idle) — *was orange* |
| Dim gray | `#5A5A5A`  | Attached, no content |

Rules preserved from the current mapping:

- Vouched means `witnessVerdict == "Real" && witnessBase == wramBase`, exactly
  as today.
- Cooldown-gray overrides only the unresolved states (Searching, Discovering,
  NoContent); the resolved family keeps reporting green/blue, and Degraded
  keeps reporting orange.
- Unknown future state names render Yellow (searching-ish), replacing the old
  gray fallback.

`PaleGreen` is deleted. `StatusDotTests` is updated to the new table.

**Cross-repo follow-up (not gating this release):** the consumer contract
`snes_offsets/docs/status-first-consumption.md` ("Status-pixel mapping
(SMWCounters)") mirrors this mapping and must get the same edit.

## 2. Coin counter

New `CoinCounter : BankedCounter`, id `coins`, default label "Coins",
serialized as `Coins`/`CoinsSaved`. Icon: new `Assets/coin.png` (asset
supplied by Andrew; wire-up + CREDITS.md entry if the source needs credit).

Semantics mirror `PowerupCounter`: collect in-level, bank on midway grab
(`$13CE` 0→1) or exit save (`$1F2E` increment), revert to last bank on death
(inherited `$0071` → 9 edge), gold alert while `total != saved`, standard
per-counter enable and "Bank on save" toggle.

Two mechanical differences from existing counters:

**Delta collects.** The game's coin counter `$0DBF` can jump by more than 1
between polls (multi-coin blocks, bursts), so `BankedCounter`'s
`bool DetectCollect` → `total++` becomes `int DetectCollectDelta` →
`total += delta`. `ExitCounter` and `PowerupCounter` return 0/1 — behavior
unchanged. `CoinCounter` reads `$0DBF`, gates on game mode `$0100 == 0x14`
(same gate as Powerups; clears its previous-value state when the gate fails),
and returns the delta from the previous poll.

**Wrap handling.** At 100 coins the game grants a 1-up and wraps `$0DBF`.
Delta rule when the gate passes and a previous value exists:

- `cur >= prev` → delta `cur - prev`.
- `cur < prev` → candidate `cur + 100 - prev`. Count it only if
  `candidate <= 15` (a plausible per-poll burst across the wrap); otherwise
  treat as a resync and count 0. The threshold also guarantees hack-shop coin
  *deductions* never register as gains. 15 is a named constant, tunable if
  live sessions show larger legitimate bursts.

**Shared bank detector.** The midway/exit bank detection currently private to
`PowerupCounter` is extracted into a small shared detector (e.g.
`MidwayExitBankDetector` with its own `PreviousByte` pair and `Clear()`), used
by both `PowerupCounter` and `CoinCounter`. Targeted extraction only — no
wider refactor.

## 3. Jumps game-mode gate (bug fix, live-confirmed)

`JumpCounter` gates on `$1935 == 1`, which is blind in custom Yoshi Houses —
confirmed live 2026-07-27: jumps don't count there. Swap the gate to
`$0100 == 0x14` exactly as `PowerupCounter` does (read game mode; on failure
or mismatch, clear the previous-value state and skip). `MoonCounter` keeps
`$1935` (backlog: the case is weak there).

## 4. Settings hint for many counters

Overflow wrap is **not** implemented (see BACKLOG.md: mid-run digit growth
would change component height mid-run). Instead, the Settings dialog shows a
friendly static hint when more than 3 counters are enabled, along the lines
of: *"If counters are cutting off, consider adding a second SMWCounters
component to the layout, one above the other, and splitting counters between
them."* Hint visibility updates as counters are toggled. Exact copy and
placement decided at implementation; no new behavior beyond the label.
